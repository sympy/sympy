Writing a pull request description
==================================

Fill out the pull request template when opening a pull request. Do not delete
or replace the template, and keep all section headings, or the pull request
will be closed.

Read the :doc:`AI Generated Code and Communication Policy
<ai-generated-code-policy>`. As required by that policy, do not use
AI-generated text to complete the pull request description, or the pull
request will be closed.

The pull request title should be a short description of what was changed.
Do not include the issue number in the title.

References to other Issues or PRs
---------------------------------

If there is an issue related to the pull request, include a link to the issue
in this section. It is important not to waste reviewers' time by skipping
this section.

If the pull request fixes an issue, write ``Fixes #NNNN`` in that exact
format, for example, ``Fixes #1234``. See GitHub's documentation on
`linking a pull request to an issue
<https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue>`_
for more information.

If the pull request does not completely fix the issue, write ``See #NNNN``,
for example, ``See #1234``. Do not write ``partially fixes #NNNN`` or use
``fix``, ``resolve``/``resolves``, ``close``/``closes`` (or any form of these
words) ahead of the issue number. GitHub's auto-close parser matches those
keywords next to a number and will close the issue regardless of what
precedes or follows them.

AI Generation Disclosure
------------------------

If the pull request includes AI-generated code or text, disclose the tool
used and specify which lines were generated. Disclosure is not required
for minor assistive tasks, such as spell-checking or code reviewing, in
primarily human-authored work. Otherwise, write ``NO AI USE`` in this section.

Do not delete this section of the template or leave it blank, or the pull
request will be closed. If you write ``NO AI USE`` and the code looks like
it was generated by AI, the pull request will be closed.

.. _pull-request-release-notes:

Release Notes
-------------

Write the release notes between the ``BEGIN RELEASE NOTES`` and
``END RELEASE NOTES`` comments in the template. Keep both comments.
The basic format is a bulleted list with the name of the subpackage and
the release note for the pull request. For example:

.. code-block:: markdown

   * solvers
     * Added a new solver for logarithmic equations.

   * functions
     * Fixed a bug with log of integers. Formerly, `log(-x)` incorrectly gave `-log(x)`.

   * physics.units
     * Corrected a semantical error in the conversion between volt and statvolt which
       reported the volt as being larger than the statvolt.

If no release notes should be included, use:

.. code-block:: text

   NO ENTRY

Use ``other`` for changes outside a submodule and names such as
``physics.mechanics`` for physics submodules. The bot checks formatting when
the description changes and adds entries to the release notes after merging.
Reload the page to see updates to its existing status comment.

Writing useful entries
~~~~~~~~~~~~~~~~~~~~~~

Describe user-visible changes, including bug fixes and performance improvements.
Use ``NO ENTRY`` for typo fixes, minor documentation changes, tests, developer
files, or refactoring that leaves user-visible behavior unchanged.

Keep each entry to one short, complete sentence, capitalized and ending with
a period. Write in the past tense for users reading the published release.
Explain observable behavior rather than implementation details; a small code
example can help. For example:

.. code-block:: markdown

   * core
     * Fixed `f(1).is_number` to return `False`, where `f = Function('f')`.

Make every bullet self-contained. Omit author names, issue numbers, and PR
numbers; the bot adds attribution and a PR link. Put supporting details in
the description. Document changes since the previous release, updating earlier
entries if an unreleased change is revised or removed.

Maintaining the release notes
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Authors and reviewers can revise entries before merging. Check the release
notes afterward and correct them manually if necessary. Highlights and
backward incompatibilities, including deprecations and removed deprecated
code, require manual entries. See :doc:`deprecations` for the deprecation
policy. Preserve the ``Changes`` and ``Authors`` headings when editing the
release notes: the bot uses them to locate the entries. The release script
generates the author list.
